# 双轴云台与 K230 人脸跟踪技术攻关

## 一、背景与目标

桌面语音伴侣原来只"能说话"，缺了"会看你"。本次目标是加装双轴舵机云台：K230 做本地人脸检测，把人脸中心坐标经 WiFi UDP 发给主控 ESP32-S3，由后者驱动水平（PAN）与俯仰（TILT）两个舵机，使云台始终"注视"画面中的人脸。

难点不在算法，而在于这是一次**跨设备、资料缺失**的联调：K230 是第三方成品套件，它跑什么脚本、往哪个地址发包、走网络还是串口，本仓库里均无线索。工作量基本花在"定位对方"和"把手感调出来"上。

涉及文件：`companion_face.c`（UDP 接收、坐标校验、控制律与主循环）、`servo.c`（舵机驱动与保活线程）、`infra/network_manager.c`（应用层静态 IP）、`nuttx/.../esp32s3_ledc.c`（PWM 引脚）。

---

## 二、硬件连接与引脚确认

舵机 PWM 由 ESP32-S3 的 LEDC 产生，经 `/dev/pwm0`（PAN）、`/dev/pwm1`（TILT）以 `PWMIOC_SETCHARACTERISTICS` + `PWMIOC_START` 输出 50 Hz 方波：

```
servo: init ok pan_fd=3 tilt_fd=4 (PAN=GPIO2 TILT=GPIO1)
```

**引脚踩了个大坑。** 最终接线是 **PAN = GPIO2、TILT = GPIO1**，但最初代码相反，而且矛盾藏在两处注释里：`[SERVO-R39]`（10-12）把 TILT 硬编码成 **GPIO4**，而 `[V517]`（10-17）注明 **GPIO4 其实是台灯继电器**。也就是说，修复前所谓"俯仰"通道一直在往台灯继电器灌 50 Hz PWM，此前"俯仰轴已验证通过"的结论随之作废。这个矛盾是靠逐条比对注释发现的，不是靠量波形。

修正在 `esp32s3_ledc.c` 的通道表里以 `[V1041] SUPERSEDES [SERVO-R39]` 标注。之所以在 C 里强制赋值而不改 Kconfig：改 `.config` 会重跑 olddefconfig → clean_context → 删掉 `chip/esp-hal-3rdparty`，代价远高于代码里写死。

## 三、通信协议

链路是 **单向 UDP 单播**：K230 → ESP32 的 `192.168.110.154:3333`。ESP32 侧 `bind(0.0.0.0:3333)`，不握手、不回包，因此对端源 IP/端口任意。报文以 `\n` 结尾（`\r` 同样接受）：

| 报文 | 含义 |
| --- | --- |
| `F,<cx>,<cy>,<w>,<h>,<conf>\n` | 有人脸 |
| `N\n` | 无人脸 |
| `F,500,500,80,80,90\n` | 心跳行，伪装成居中的假人脸 |

`cx/cy/w/h` 是相对画面的 **千分比坐标 0..1000**，`conf` 为 0..100；K230 侧按 8~10 Hz 发送，`N` 间隔约 0.5 s（脚本 `NOFACE_HZ = 2`）。

两条硬约束：`F,` 之后**必须正好取到 5 个整数**，否则整行丢弃（`short=` 计数），避免用半截数据驱动舵机；人脸丢失时应静默，**不要持续补发** `F`（实测那样 5~8 s 就会崩）。

## 四、K230 侧定位过程：从"网络上找不到"到"它就插在电脑上"

这是投入最大、也最能体现排查路径的一段。开局的全部线索只有一条注释："与小智固件已验证的实现完全一致，K230 侧脚本零改动"。

**第一阶段：固件侧主动探测，四条路全部否定。**

1. **ARP 观察器**：改 `nuttx/net/arp/arp_input.c`，在判断"是不是问我的"之前插桩——ARP 请求是广播帧，理论上能读出任何设备的解析目标。观测 450 s，目标全是网关 `.1` 与 DHCP 后的重复地址检测，**零 K230 特征**。（须用 `syslog()` 而非 `ninfo()`：本 build 无 `CONFIG_DEBUG_INFO`，`ninfo()` 编译为空。）
2. **网段扫描**：新增 `companion_scan.c`（313 行），用 UDP 探测包逼对方 ARP 应答再读 MAC，扫遍 `/24` 得 **13 台在线主机**。
3. **端口指纹**：全网段只有 `.138` 开端口（5555 / 8000），**K230 候选 0 条**；此前按 OUI 怀疑的两台 Espressif 设备 11 个端口全关，更像插座。
4. **WiFi 扫描**：走 `wapi`（符号已在现有 ELF 里，不用改 Kconfig），只见 `vox3`/`3124`/`8888` 三个 SSID，BSSID 仅第 4 字节不同、与网关 MAC 只差 U/L 位，**同属一台物理 AP**。"ESP32 应跑 SoftAP 给 K230 连"同时被 `.config:349-351` 否决。

结论：**K230 不在这个网段，且无线侧不可见。**

**第二阶段：掉头查物理侧，一击命中。**

枚举 USB 后局面翻转：K230 一直就插在这台电脑上。它在网络扫描里缺席，只说明它当时的 IPv4 身份不在那 13 台之中——在 `CONFIG_NET_ARPTAB_SIZE=16` 的 ARP 表容量下，这本来就不能当作"不在线"的判据。

```
COM33 | VID:PID=1209:ABD1 SER=001000000         <- K230（CanMV，厂商 Kendryte）
COM32 | VID:PID=303A:1001 SER=90:70:69:16:2A:3C <- 本项目这块 AI-VOX3
COM34 | VID:PID=303A:1001 SER=14:C1:9F:2A:C1:A8 <- 另一块 ESP32-S3
```

顺带纠正一个此前的错误：本机 WiFi MAC 是 `90:70:69:16:2A:3C` 而非 `14:C1:9F:...`，整轮"按 OUI 找 K230"的前提随之作废。

**关键技巧：** K230 的 USB 是复合设备，`MI_00` 为串口（COM33），`MI_02` 是 **MTP**（`Service=WUDFWpdMtp`），在"此电脑"里可像 U 盘一样直读其 SD 卡，无需拆卡或改设备：

```python
shell = win32com.client.Dispatch("Shell.Application")
dev  = [i for i in shell.NameSpace(17).Items() if "CanMV" in i.Name][0]
sd   = shell.NameSpace(dev.Path + "\\sdcard")   # 子目录只能这样取
dest = shell.NameSpace(local_dir); dest.CopyHere(item, 4|16|512|1024)
```

卡内 23 项，是 Yahboom K230 套件。`main.py` 是 bootloader：连 WiFi SSID `3124` → 从远端 HTTP 拉业务脚本 → 失败则回落到 SD 卡缓存 `xz_face.py`（49233 B，实际运行的那份）→ `exec`。**实际在跑的代码可能根本不是卡上那份。**

**真根因就在这份脚本里**，与 ESP32 的地址只差 1：

```python
# xz_face.py:20-21
VOX3_IP   = "192.168.110.154"   # AI-VOX3 的 IP（arp 扫出来的，MAC 90-70-69-16-2a-3c）
VOX3_PORT = 3333
```

注释里的 MAC 正是本项目的 COM32 那块板，说明它当初确实是 `.154`；而 ESP32 现在由 DHCP 拿到 `.155`。所有包都被发往一个已经不存在的地址。

顺带解释了两件事：

- **为什么 ARP 观察器零命中**：K230 的 ARP 缓存里还留着 `.154` 的旧条目 ⇒ **不再发 ARP 请求**，包被单播到一个早已消失的 MAC 后丢弃。这是"抓不到 ARP ≠ 对方没在发"的活标本。
- **为什么 COM33 串口零输出**：实际执行的脚本 `DEBUG=False`，日志走 UDP 发往 `192.168.110.151`，串口重插后依然静默。**"串口无输出"不能再作为 K230 是否在跑的判据。**

K230 的真实身份：**IP `192.168.110.12`**（历史记录 `.11`，DHCP 漂了），连 SSID `3124`。

## 五、网络打通：应用层静态 IP

K230 不可改（目的地址写死），只能**让 ESP32 去迁就它**：应用层把 wlan0 覆写成 `192.168.110.154`。开机路径是 `agent_main.c:309 network_wait_connected(30000)` → `ensure_dns()`，因此钩子加在 `ensure_dns()` 里、**掩码之后默认路由之前**——`SIOCSIFADDR`（`netdev_ioctl.c:343`）只写 `d_ipaddr`，不动掩码与路由。`:1042` 的 `system("renew")` 看着像对的落点，实际只在 `set_wifi` / BLE 配网路径执行，开机走不到。

`ensure_static_ip()` 先 `netlib_get_ipv4addr()` 读回比对，相同即 return，幂等且安静，可挂在每次"已联网"事件上。**全程不动 Kconfig**：netinit 照常关联 AP 并 DHCP，应用层再覆盖——风险小、可回滚，路由与兜底行为都不丢。

实测：

```
5.41  [netmgr] Found iface wlan0 addr 192.168.110.155   <- DHCP
5.41  [V1041] static ip 192.168.110.154 rc=0            <- 应用层覆盖
17.88 / 21.18  ... .154                                 <- 没被 DHCP 续租冲回
5.85  [V1036] EXTERNAL from=192.168.110.12 : N          <- 真 K230 的报文进来了
```

## 六、控制律设计

控制律以 20 Hz 独立运行（`CF_LOOP_PERIOD_MS = 50`），流程是：**协议解析 → 坐标越界丢弃 → 跳变拒绝 → EMA 低通 → 绝对映射 → 限幅 → 每拍限速逼近**。

核心两条：

```
pan  = 90 + (cx - 500) x CF_ABS_PAN_GAIN
tilt = 90 - (cy - 500) x CF_ABS_TILT_GAIN
```

`cx/cy` 为千分比坐标，中心 500。之所以敢放开增益，是因为这是**开环系统**：`COMPANION_FACE_ON_GIMBAL = 0`（唯一定义在 `companion_face.h:24-25`，全树无覆盖），摄像头固定在桌面、不随云台转动，**转头不会改变摄像头看到的内容 ⇒ 无反馈通路 ⇒ 不会过冲、不会自激**。另一条 `#if` 分支（摄像头架在云台上）走负反馈比例律，本项目用不到。

其余策略：收到 `N` 后 `g_face.x` 置 -1，`fresh` 立即为假，`CF_RECENTER_MS` 后回中 90/90 并按 `CF_SLEW_PER_TICK` 限速逼近，避免猛甩；丢失期间**不扫视**——摄像头固定，转头找不到人，只会白耗舵机寿命。限幅分层：控制律 `10..170` / `20..160`，舵机层 `5..175` 未动。

## 七、两轮调参与实测数据

### 第一轮（V1043）：用户反馈"太慢"

量化先行：`face idle` 心跳里 `cur` 与 `tgt` 始终相等（如 `cur=63,97 tgt=63,97`），说明**舵机是到位了的**，慢的是目标角本身在原地摆、几秒才挪一点：

```
17.55 pan=79 → 17.86 pan=65 → 19.05 pan=70 → 19.68 pan=65 → 23.42 pan=75
```

进一步发现真正的闸门不是 `CF_DEADBAND = 20‰`，而是控制律里硬编码的 `> 2`：`pan` 侧要求 dx ≥ 46.2‰ ≈ 3.06°，`tilt` 侧 ≥ 58.8‰ ≈ 3.00°，而死区更松，从来不是瓶颈。此外 ESP32 侧还有一层 EMA（alpha 0.375）与 K230 侧的 `SMOOTH_ALPHA = 0.5` **叠加**，迟滞是两处累积的结果。

改动：`CF_SLEW_PER_TICK` 3→12（60°/s → 240°/s）、`CF_DEADBAND` 20→10、新增 `CF_MIN_DELTA_DEG` = 1 取代硬编码 `> 2`、`CF_RECENTER_MS` 2000→900、`CF_EMA_NUM` 3→6（alpha 0.375→0.75）。

端到端阶跃响应估算：**20° 阶跃从约 1130 ms 降到约 500 ms，40° 阶跃从约 1470 ms 降到约 700 ms**。瓶颈由"EMA + slew 双瓶颈"迁移到只剩**舵机保活线程 200 ms 的那一拍**。

两处刻意没做到极致：死区只压到 2.0°，因为 `servo.c` 的 `SERVO_DEFAULT_DEADBAND = 2°` 会静默丢弃更小的目标角，再压毫无收益；EMA 保留而非删除，因为跳跃拒绝窗口约 ±150‰（≈ ±10°），裸数据一帧就能让头猛甩，且上游未必自带平滑。

### 第二轮（V1044）：用户反馈"幅度太小"

从 `_v1042_test.txt` 的 1028 个真实 F 包统计：**pan 只在 63~93 之间（跨度 30°），tilt 只在 93~108 之间（跨度 15°）**，而当时的限幅是 30~150（±60°）与 50~130（±40°）——**分别只用了 1/4 和 1/8**。校验 `cx=73 ⇒ 90 - 427 x 0.065 = 62.2 ≈ 63` 吻合，说明不是 bug，是增益过于保守：0.065 是按物理视场角算出的"精确对准值"（脸到画面边缘时头部只转 32.5°），精确但对观感来说就是"几乎不动"。

改动：`CF_ABS_PAN_GAIN` 0.065→**0.16**（2.46×）、`CF_ABS_TILT_GAIN` 0.051→**0.14**（2.75×），限幅同步放宽到 `10..170` / `20..160`。增益与限幅**精确配套**：`500‰ x 0.16 = 80° ⇒ 90 ± 80 = 10..170`，正好等于新限幅。

本轮还堵了一个真漏洞：跳变阈值随人脸宽度放大（最高 600），因此串扰产生的 `cx=3077`（先被 `clampi` 折成 1000）跳跃幅度 500 < 600，**会被接受**。增益放大 2.5 倍后，一行脏数据就能把舵机砸到 170° 限位。修复是在 `parsed++` 之前加一道 `cx/cy` 必须落在 0..1000 的**整帧丢弃**（不夹紧——整行已坏）。

实机结果：**pan 90~162（跨度 72°）、tilt 41~140（跨度 99°），脏数据告警 0 次**，相比调整前的 30° / 15° 有显著改善。此前 V1042 的基准同样显示 duty 随角度真实变化（1154 条报文，F 1028 / N 118，源 `192.168.110.12`；`ch=1 angle=93→4967`、`108→5242`）。

## 八、踩坑记录

1. **阻塞 socket 会卡死整个线程。** `cf_open_socket()` 未设 `O_NONBLOCK`，而 `cf_poll_socket()` 是 `for(;;) { recvfrom(); ... }`，没包时永久阻塞，**控制律、舵机下发、10 s 健康报告全部不执行**——这就是"240 s 零输出"的真原因（不是日志丢了，是线程没跑到打印点）。修法是 `fcntl(fd, F_SETFL, fl | O_NONBLOCK)`，空队列返回 EAGAIN，被现有 `if (n < 0) break` 正好接住。**给"没输出"下结论前，先确认线程有没有跑到那个打印点。**

2. **自检包要发到网卡自身地址。** V1031 的自检线程最初设计发往 `127.0.0.1:3333`，而 V1035 抓到的自测包源地址是 `192.168.110.155`（wlan0 自身）——本 build 下回环地址不可依赖。

3. **数据源发包频率必须 ≥ 控制律频率。** 早期自检每包间隔 2 s，控制律却跑 20 Hz，中间约 40 次空迭代被判定"人脸丢失"并回中，扫掠刚起步就被拉回（`moved=0`）。改为 8 Hz × 40 包平滑扫掠（每步 15‰，远低于跳变阈值 250）后立刻正常（`moved=32`）。

4. **舵机链路有两个真值源。** `servo_move()` 只把角度写进 `g_limits[].target` 记账，真正写 PWM 只在 200 ms 一拍的保活线程里 ⇒ 任何绕开它的直接写入会在 200 ms 内被拉回旧目标。修复是在 `servo_set_ch()` 里同步 `g_limits[ch->idx].target`；但**无条件同步会把长行程截断**：每拍预算 `36°`，若 cur=0 想到 109，第一拍写 36 后 target 被同步成 36，下一拍见 `target == cur` 直接 return，**舵机永久停在半路** ⇒ 保活线程的两类写入必须走保留 target 的变体。

5. **DRAM 只剩 112 字节。** `_edata = 0x3fccff90`，余量 112 B；一个 384 B 的静态数组就报 `region dram0_0_seg overflowed by 272 bytes`。更反直觉的是**删代码并不让 DRAM 变松**：V1042 删掉整套诊断后 `_edata` 纹丝不动，因为 `.dram0.data` 尾部被固定目标占着。**判断余量要看 `_edata`，不能看 elf-size 的 data/bss 增减。**

6. **诊断代码绝不能留在交付版。** V1042 清理时，`companion_scan.c` 除从 Makefile 移出还必须**删掉陈旧 `.o`**——否则 `libapps.a` 继续把它链进去，向 254 个地址发 UDP 的扫描包照旧出网。同时删掉 `cf_selftest`（开机自测会发假 `F,...` 报文，真 K230 接入后就是污染源）与 ARP 观察器；**刻意保留** `[V1030]` 心跳与 `[V1036] EXTERNAL`——一次性探测用完即删，链路心跳必须常驻。

7. **验收要在二进制层面复核。** 串口会串扰出假标签（日志里出现过并不存在的 `[V10397`）。判据是 `open(bin,'rb').read().count(b'[TAG]')`，不是 grep 串口文本。

## 九、遗留问题

1. **最终手感待主观确认。** v1044 已烧录，实测 pan 90~162、tilt 41~140，pan 距上限 170 只剩 8°，可能打满。过头则退档 `CF_ABS_PAN_GAIN` 0.11~0.13、`CF_ABS_TILT_GAIN` 0.09~0.11；发抖则 `CF_MIN_DELTA_DEG` 回调 2、`CF_EMA_NUM` 回调 4；仍嫌慢的唯一剩余延迟源是 `SERVO_KEEPALIVE_PERIOD_MS` 200→100，或调 K230 侧 `SMOOTH_ALPHA` / `SEND_HZ`（SD 卡经 MTP 可写，需用户同意）。
2. **静态 IP 的长期保险。** 若 DHCPC 续租把地址改回 `.155`，覆盖会被冲掉（实测 21 s 时仍是 `.154`）。能周期重断言的 `iface_poll_thread()` 在 `CONFIG_AI_AGENT_NET_RPMSG` 分支，本板不编译。彻底做法是在路由器上给 MAC `90:70:69:16:2a:3c` 绑定静态 DHCP；退路是经 MTP 改 K230 SD 卡上的 `VOX3_IP`。
3. **云台控制权残余争抢。** `companion_mood.c` 的 `servo_nod()` / `servo_shake()` 内有约 660 ms 的 `usleep`，期间与保活线程争抢云台，次要问题，未处理。

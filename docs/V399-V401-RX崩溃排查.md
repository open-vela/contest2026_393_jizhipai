# V399–V401：I2S RX 首帧到达后的崩溃排查

## 结论先行

开机采集自检一跑起来，RX **确实收到了第一帧**，但紧接着系统必崩。崩溃点**不在**音频驱动，
也**不是**中断栈容量问题，而是 **WiFi 闭源 FIQ 在 RX 中断期间触发了一次异常**，
并且这次异常的转储过程又踩了一次空指针，把第一现场掩盖掉了。

为了让设备可用，V401 把采集自检做成了编译期开关（`CAPTURE_PROBE` / `V401_CAPTURE_PROBE`），
默认置 `0`；置 `1` 即可原样复现，继续排查。

## 现场证据

### 1. RX 链路本身是通的

```
[RXEOF] first SUC_EOF! isr=1        <- GDMA EOF 中断真的来了
[RXBOUNCE] ...                      <- 数据已回灌到 PSRAM 缓冲
[AUDIO-R42] xfer ret=0              <- 一次传输成功完成
```

也就是说：**GDMA 描述符、EOF/OWNER 位、I2S 时钟、ES8311 初始化都是对的**。
这推翻了此前"I2S RX 根本没起来"的假设。

### 2. 崩溃转储

```
EXCCAUSE = 0x001c
VADDR    = 0x00000000
调用链   irq_dispatch -> wDev_ProcessFiq -> xtensa_user
          -> xtensa_user_panic -> _assert -> up_saveusercontext
```

两条关键信息：

- `wDev_ProcessFiq` 是 **ESP32-S3 WiFi 的闭源 FIQ**，它抢占了 GDMA RX 中断；
- `VADDR=0` 说明 `up_saveusercontext` 被要求向**空指针**保存寄存器现场
  （`tcb->xcp.regs == NULL`），这是**二次崩溃**，真正的第一现场被它盖住了。

### 3. 排除中断栈

| `CONFIG_ARCH_INTERRUPTSTACK` | 崩溃 |
| --- | --- |
| 4096 | 崩 |
| 6144 | 崩 |
| 8192 | 崩 |

实测中断栈峰值只用了 **336 字节**（栈顶 − sp = 336）。三档容量表现完全一致，
**栈容量不是原因**。V400 试图"等链路就绪再开采集"来避开 WiFi 关联风暴期的密集 FIQ，
同样崩溃——说明不是时序密度问题，是并发/内存冲突。

## 当前处置（V401）

| 位置 | 改动 |
| --- | --- |
| `packages/ai_agent/src/agent_main.c` | `#ifdef CONFIG_AI_AGENT_VOICE_BOOT_TEST` → `#if 1`，并加 `CAPTURE_PROBE` 开关 |
| `packages/ai_agent/src/voice/audio_capture_native.c` | `native_capture_selftest()` 加 `V401_CAPTURE_PROBE` 开关，置 0 时直接返回 |
| `nuttx/.../esp32s3_i2s.c` | `I2S_DMABUF_SLOTS` 3 → 2（给 8192 中断栈腾 DRAM） |
| `.../configs/ai_agent/defconfig` | `CONFIG_ARCH_INTERRUPTSTACK` 6144 → 8192 |

### 顺带修掉的一个坑

`CONFIG_AI_AGENT_VOICE_BOOT_TEST` 定义在**外部包** `packages/ai_agent` 的 Kconfig 里。
nuttx 每次 `olddefconfig` 都会把这个符号丢掉，所以 V396/V397 里被 `#ifdef` 包住的
自检代码**从来没被编译进去**——"自检没跑"其实是这个原因，不是被我们关掉的。
V398 起改成 `#if 1` 显式控制。
